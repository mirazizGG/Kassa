# Развёртывание PHP-версии Kassa на cPanel

Инструкция на день переезда. Рассчитана на обычный shared-хостинг с cPanel,
без root-доступа.

**Ключевое правило: магазин должен быть закрыт, пока идёт перенос.** Продажи,
проведённые в старой базе после снятия копии, на новый сервер не попадут.

---

## Чем эта версия отличается от Python

| | Python (Passenger) | PHP |
|---|---|---|
| Память на процесс | ~218 МБ | ~2 МБ на запрос |
| Простой | процесс висит в памяти | ноль процессов |
| Холодный старт | 1–3 с | нет (opcache) |
| Статика (JS/CSS) | через приложение | напрямую веб-сервером |
| Telegram-бот | не работал на шареде | не входит в состав |

Интерфейс тот же самый — это тот же собранный React. API совпадает по путям
и по формату ответов, поэтому фронтенд не изменился ни на строку.

**Чего в PHP-версии нет:** Telegram-бота и обновления из приложения. Бот
требует постоянно живущего процесса, которого на шареде не бывает; в Python
он там тоже не работал. Отметки прихода/ухода сотрудников через бота,
соответственно, недоступны — данные в таблице `attendance` сохраняются и
видны на странице «Давомат», но новые записи пока делать нечем.

---

## 0. Что нужно под рукой

- Доступ в cPanel и по SSH (или File Manager, если SSH нет).
- Домен, уже добавленный в cPanel.
- Копия боевой базы: `backend/market.db` со старого сервера.
- Папка `backend/uploads/` оттуда же — там фотографии накладных. В дампе базы
  их нет, копируются отдельно.

Проверьте версию PHP: cPanel → **Select PHP Version**. Нужна **8.1 или новее**.
Включите расширения: `pdo_mysql`, `mbstring`, `openssl`, `zip`, `fileinfo`,
`curl`, **`opcache`**.

`opcache` включить обязательно — без него PHP разбирает исходники заново на
каждом запросе. Настройки лежат в `public/.user.ini`, cPanel читает этот файл
сам. Если хостинг запрещает менять какие-то значения, они просто игнорируются
и приложение всё равно работает.

Если доступен **APCu** — включите и его: кэш тяжёлых выборок переедет из
файлов в память. Не обязателен, без него всё работает через файлы.

## 1. База данных

cPanel → **MySQL Databases**:

1. Create Database: `kassa` → полное имя будет вида `erkatoyu_kassa`
2. Create User: `kuser` → полное имя `erkatoyu_kuser`, придумайте сильный пароль
3. Add User To Database → **All Privileges**

Запишите оба полных имени — они пойдут в `DATABASE_URL`.

Проверка из SSH:

```bash
mysql -u erkatoyu_kuser -p erkatoyu_kassa -e "SELECT VERSION();"
```

## 2. Файлы

Загрузите папку `php/` в домашний каталог, например в `~/kassa`:

```bash
mkdir -p ~/kassa
tar -xzf ~/kassa-php.tar.gz -C ~/kassa
ls ~/kassa        # app  bin  public  .env.example  DEPLOY.md
```

Структура намеренно такая, что **исходники лежат выше document root**:

```
~/kassa/
  app/        <- код, из веба недоступен
  bin/        <- скрипты для консоли
  logs/       <- журнал ошибок
  backups/    <- резервные копии
  public/     <- document root, только сюда смотрит браузер
    uploads/  <- фото накладных (отдаёт веб-сервер, код здесь запрещён)
  .env        <- настройки, из веба недоступны
```

### Document root

cPanel → **Domains** → у вашего домена → Edit → Document Root →
`/home/erkatoyu/kassa/public`

Это самый надёжный вариант: `app/` и `.env` физически вне зоны веб-сервера.

**Если сменить document root нельзя** — перенесите содержимое `public/` в
`public_html/`, а `app/` и `bin/` положите рядом с `public_html/`:

```
~/kassa/app/
~/kassa/bin/
~/kassa/.env
~/public_html/     <- index.php, .htaccess, assets/, index.html
```

и в `~/public_html/index.php` первая строка `require` уже указывает на
`dirname(__DIR__) . '/app/bootstrap.php'` — поправьте её на
`'/kassa/app/bootstrap.php'`.

## 3. Настройки

```bash
cd ~/kassa
cp .env.example .env
chmod 600 .env
php -r "echo bin2hex(random_bytes(32)), PHP_EOL;"   # ключ, скопируйте
nano .env
```

Обязательно заполнить:

| Переменная | Чем |
|---|---|
| `APP_ENV` | `production` |
| `SECRET_KEY` | ключ из команды выше (не короче 32 символов) |
| `DATABASE_URL` | `mysql://erkatoyu_kuser:ПАРОЛЬ@localhost/erkatoyu_kassa` |
| `PRIMARY_ADMIN_PASSWORD` | сильный пароль (после переноса не используется) |
| `SHOP_TIMEZONE` | `Asia/Tashkent` |

`ALLOWED_ORIGINS` оставьте **пустым** — интерфейс и API на одном домене, CORS
не нужен.

Если в пароле есть `@ : / ? #` — закодируйте их (`@` → `%40`), иначе адрес
разберётся неправильно.

## 4. Перенос данных

**Порядок важен:** сначала перенос, потом первый вход. Иначе приложение
создаст своего `miraziz`, база перестанет быть пустой, и скрипт переноса
откажется работать.

### 4.1 На старом сервере

Закройте все смены. Запустите старую программу **один раз новой версией** —
она переведёт время смен в UTC. Без этого шага скрипт переноса откажется
работать, и правильно сделает: иначе время смен уехало бы на 5 часов.

```bash
cp backend/market.db market.db.perenos
```

Загрузите `market.db.perenos` и папку `uploads/` на новый сервер.

### 4.2 Подготовка схемы

```bash
cd ~/kassa
php bin/setup.php
```

### 4.3 Сухой прогон

Ничего не пишет, показывает только количество строк по каждой таблице.

```bash
php bin/migrate.php --source ~/market.db.perenos --dry-run
```

Сверьте числа с тем, что показывает программа в магазине: товары, клиенты,
продажи. Не сошлось — **остановитесь** и разберитесь.

### 4.4 Перенос

```bash
php bin/migrate.php --source ~/market.db.perenos
```

Скрипт:

1. проверит, что миграция времени смен на источнике выполнена;
2. откажется работать, если целевая база не пуста;
3. скопирует таблицы в порядке внешних ключей;
4. **сдвинет счётчики `AUTO_INCREMENT`** — без этого первая же новая продажа
   упала бы с `duplicate key`;
5. сверит количество строк по каждой таблице.

Последняя строка должна быть `Ko'chirish muvaffaqiyatli tugadi.`
Если вместо неё `KO'CHIRISHDA FARQ BOR` — базу не использовать, выяснять причину.

**Пароли сотрудников переезжают как есть.** Формат хэша тот же, что писала
Python-версия, поэтому все входят своими старыми паролями.

### 4.5 Накладные

```bash
mkdir -p ~/kassa/public/uploads/invoices
cp -r ~/uploads/invoices/* ~/kassa/public/uploads/invoices/
chmod -R 755 ~/kassa/public/uploads
```

Папка лежит **внутри** `public/` намеренно: веб-сервер отдаёт фото напрямую,
PHP при этом не запускается вовсе. Выполнение любого кода в этой папке
запрещено отдельным `public/uploads/.htaccess` — не удаляйте его.

Проверьте, что фото открывается: `https://ваш-домен/uploads/invoices/<имя файла>`.

### Если магазин новый

Переносить нечего — достаточно `php bin/setup.php`. Он создаст таблицы и
первого админа с паролем из `PRIMARY_ADMIN_PASSWORD`.

## 7. Резервные копии через cron

cPanel → **Cron Jobs** → Add New Cron Job.

Common Settings: Twice a day (или вручную `0 12,22 * * *`)

Command:

```
/usr/local/bin/php /home/erkatoyu/kassa/bin/backup.php >> /home/erkatoyu/kassa-backup.log 2>&1
```

Путь к php уточните: `which php`.

Проверить вручную:

```bash
php ~/kassa/bin/backup.php
ls -la ~/kassa/backups/
```

В `backups/` появляются два вида файлов:

- `backup_*.sql.gz` — база;
- `uploads_*.zip` — фотографии накладных, которых в дампе нет.

У каждого вида своя глубина хранения, они не удаляют файлы друг друга.
**Для полного восстановления нужны оба файла за одну дату.**

Скачивайте копии к себе: cPanel → File Manager → `kassa/backups`.
Единственная копия на том же сервере, где база, — это не копия.

**Отключить бэкапы:** `BACKUP_ENABLED=false` в `.env`. Тогда и кнопка в
интерфейсе честно скажет, что резервирование выключено, и cron ничего не
сделает.

### Восстановление из копии

```bash
gunzip -c ~/kassa/backups/backup_20260922-120000.sql.gz | mysql -u erkatoyu_kuser -p erkatoyu_kassa
cd ~/kassa && unzip -o backups/uploads_20260922-120000.zip -d uploads/
```

```bash

```

Ожидается `{"status":"ok","version":"2.0.0-php","runtime":"php-8.x",...}`.

Дальше пройдите список:

- [ ] `https://ваш-домен` открывается, замок зелёный
- [ ] вход под `miraziz` работает **старым** паролем (перенесённым, не из `.env`)
- [ ] в справочнике товаров те же позиции и остатки, что были в магазине
- [ ] у клиентов сохранились долги и бонусы
- [ ] история продаж на месте, время показывается **правильно** (не сдвинуто на 5 часов)
- [ ] открывается смена, проходит пробная продажа, закрывается смена
- [ ] пробная продажа возвращается, остаток восстанавливается
- [ ] фото накладной открывается на странице «Фирмалар»

- [ ] cron-бэкап отработал вручную и создал два файла
- [ ] `curl -s https://ваш-домен/health` отвечает быстрее 100 мс

## Обновление версии

```bash
cd ~/kassa

# 1. копия ДО обновления
php bin/backup.php

# 2. распаковать новые файлы поверх
tar -xzf ~/новый-архив.tar.gz -C ~/kassa

# 3. обновить схему (безопасно запускать повторно)
php bin/setup.php
```

**После выкладки обязательно сбросьте кэш скомпилированного кода.** PHP держит
разобранные файлы в памяти и перечитывает их с диска не чаще раза в минуту
(`opcache.revalidate_freq=60`). В эту минуту часть файлов берётся новая, часть
старая — и приложение может вести себя необъяснимо, вплоть до ошибки 500.

Самый быстрый способ:

```bash
cd ~/public_html
printf '%s' '<?php opcache_reset(); echo "ok";' > __reset.php
curl -sk https://smart-kassa.uz/__reset.php && rm -f __reset.php
```

Из консоли `opcache_reset()` не поможет: у командной строки своя память,
отдельная от веб-сервера. Либо через панель: **cPanel → Select PHP Version →
Restart PHP**.

Скрипт `deploy/02-switch.sh` делает это сам.

Делайте это после закрытия магазина.

## Если что-то пошло не так

**500 или белый экран.** Смотрите `~/kassa/logs/php-error.log`. Чаще всего:
не заполнен `SECRET_KEY`, неверный `DATABASE_URL`, или папка `logs/` не
доступна для записи.

**«Baza bilan aloqa yo'q».** Неверный `DATABASE_URL` или пользователь не
добавлен к базе. Проверьте:
`mysql -u erkatoyu_kuser -p erkatoyu_kassa -e "SELECT 1;"`

**500 на весь сайт, а `~/kassa/logs/php-error.log` ПУСТОЙ.** Значит ошибка в
`.htaccess`, и до PHP выполнение не доходит. Проверяется так:

```bash
cd ~/public_html
echo '<?php echo "PHP OK ", PHP_VERSION;' > probe.php
mv .htaccess /tmp/ht.bak
curl -s "https://ваш-домен/probe.php?t=$RANDOM"     # заработало -> виноват .htaccess
mv /tmp/ht.bak .htaccess
```

Дальше добавляйте директивы по одной и проверяйте после каждой.

**Чего в `.htaccess` здесь намеренно НЕТ:**

- `SetEnv` — требует `mod_env`. На ahost.uz он не загружен, и Apache отвечает
  500 на весь сайт. Путь к ядру приложения задаётся файлом
  `public_html/.kassa-app-path`, а не переменной окружения.
- `Options` — требует `AllowOverride Options`, разрешён не везде.

**После выкладки PHP стал 7.4 вместо 8.3.** Потерян блок cPanel из `.htaccess`:

```
# php -- BEGIN cPanel-generated handler, do not edit
<IfModule mime_module>
  AddHandler application/x-httpd-ea-php83___lsphp .php .php8 .phtml
</IfModule>
# php -- END cPanel-generated handler, do not edit
```

Без него домен откатывается на версию по умолчанию для аккаунта. Скрипт
переноса сохраняет этот блок сам; при ручной правке — не удаляйте.

**Все запросы возвращают 401.** Веб-сервер съедает заголовок `Authorization`.
В `public/.htaccess` за это отвечает блок `RewriteCond %{HTTP:Authorization}` —
убедитесь, что файл на месте и `mod_rewrite` включён.

**Открывается голый JSON вместо интерфейса.** `index.html` не лежит рядом с
`index.php`. Скопируйте содержимое `frontend/dist/` в `public/`.

**Страница открывается, но магазин пустой.** Перенос не выполнялся. Проверьте:
`mysql -u erkatoyu_kuser -p erkatoyu_kassa -e "SELECT COUNT(*) FROM products;"`

**Время на 5 часов не то.** Перед переносом не запустили старую программу
новой версией. Восстановитесь из `market.db.perenos` и повторите шаг 4.

**Фото накладных не открываются.** Папка должна быть в
`~/kassa/public/uploads/invoices/` и иметь права на чтение (755). Проверьте,
что файл физически на месте:
`ls ~/kassa/public/uploads/invoices/ | head`

**Ошибка «Directory not allowed here» в логе Apache.** В `.htaccess` попал
блок `<Directory>` — он допустим только в конфигурации сервера. В поставке
его нет; если правили файл вручную, уберите.
