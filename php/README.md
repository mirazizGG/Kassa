# Kassa — PHP

Полный перенос бэкенда SmartKassa с Python (FastAPI) на PHP 8.1+.
Интерфейс не изменился: это тот же собранный React.

Развёртывание — [DEPLOY.md](DEPLOY.md).

---

## Зачем переносили

На shared-хостинге Python работает через Passenger: долгоживущий процесс,
который держит в памяти весь фреймворк. Замеры на боевом сервере:

| | Python (Passenger) | PHP |
|---|---|---|
| Память | **218 МБ** на процесс | **2 МБ** на запрос |
| 5 одновременных запросов | ~1,1 ГБ | ~10 МБ |
| Простой | процесс висит | ноль процессов |
| Холодный старт | 1–3 с | нет |
| Загрузка каркаса | секунды | 2,5 мс |
| Файлов на запрос | сотни модулей | **9** |

Дело не в скорости языка, а в модели процесса. PHP на cPanel — родной:
запрос обработан, процесс умер, память освобождена. Node.js эту проблему
не решил бы — там та же схема, что у Python.

## Замеры на реальном объёме

База: **60 000 чеков, 210 000 позиций, 150 000 записей аудита, 49 МБ.**
Это примерно два года работы оживлённого магазина.

| Страница / запрос | Было | Стало | |
|---|---:|---:|---|
| График прибыли, 30 дней | 316 мс | **13 мс** | 24× |
| Топ товаров | 275 мс | **4 мс** | 63× |
| Аудит с поиском | 48 мс | **9 мс** | 5× |
| Расходы | 38 мс | **9 мс** | 4× |
| Статистика (дашборд) | 28 мс | **4 мс** | 7× |
| Активная смена | 26 мс | **3 мс** | 7× |
| История смен | 26 мс | **5 мс** | 5× |
| Каталог целиком | 26 мс | **10 мс** | 2,6× |
| **Сумма по 20 запросам** | **1031 мс** | **185 мс** | **5,6×** |

Пропускная способность: **~72 запроса/с на один процесс**, 0 ошибок.
При 30 000 посетителей в месяц (пик ~1,2 запроса/с) это шестидесятикратный
запас — на одном процессе.

### Что именно дало выигрыш

**Графики сканировали всю историю.** Запрос группировал дни через `CASE`,
но общего ограничения по датам не имел: база читала все 210 000 строк, а
`CASE` почти все обнулял. График за 30 дней перебирал два года. Добавлено
общее окно — 316 мс превратились в 13.

**Топ товаров пересчитывался на каждый запрос.** Группировка по всей истории
продаж. Список меняется за минуты, а не за секунды, поэтому он кэшируется на
5 минут. **Остаток при этом читается живым** — в кассе не должно быть
устаревшего числа на полке.

**Составные индексы вместо одиночных.** `(cashier_id, status, created_at)`
обслуживает и расчёт смены, и список кассира. Одновременно удалены семь
индексов, ставших префиксами составных: каждый лишний индекс замедляет
**запись**, а касса пишет постоянно.

**Расчёт кассы смены — один запрос вместо четырёх.** Три подсчёта (наличные
долги, наличные расходы, наличные возвраты) переехали в подзапросы. Формула
не изменилась ни на знак.

**Счётчик аудита кэшируется на 30 секунд.** Поиск идёт по `%тексту%`, индекс
там не работает — база читает все 150 000 строк. Сами записи всегда живые,
кэшируется только число для пагинации.

**Страница аудита опрашивала сервер каждые 15 секунд.** Оставленная открытой
во время проверки, она означала четыре полных сканирования в минуту. Стало
60 секунд — для журнала истории этого достаточно.

**Лишний `COUNT(*)` в каталоге.** Без пагинации клиент получает весь список,
то есть общее количество — это и есть число возвращённых строк. Касса запрашивает
каталог чаще всего, и каждый раз это был лишний поход в базу.

**OPcache** (`public/.user.ini`) — +13% на замере. PHP перестаёт разбирать
исходники на каждом запросе.

### Что попробовал и убрал

**ETag / 304.** Работает на уровне HTTP (проверено: 1,4 МБ → 0 байт), но
браузер **не кэширует ответы на запросы с заголовком `Authorization`** — а к
API идут только такие. `Cache-Control: public` заставил бы кэшировать, но
тогда промежуточный кэш мог бы отдать историю продаж кассира постороннему.
Для кассы цена неприемлема. При этом md5 по телу ответа сервер считал бы
всегда — то есть чистый расход без отдачи. Убрано, причина записана в коде.

Повторные загрузки и так не бьют по серверу: TanStack Query держит результат
5 минут на клиенте.

## Что осталось прежним

**API совпадает по путям и формату ответов** — это было условием переноса,
поэтому React-фронтенд не изменился ни на строку. Проверяется сравнением
ответов: те же поля, те же типы, те же коды ошибок, тот же `{"detail": "..."}`.

**Пароли переезжают как есть.** Хэши в формате passlib `pbkdf2_sha256`
читаются и пишутся один в один, поэтому сотрудники входят своими старыми
паролями, а обе версии понимают хэши друг друга.

**Вся денежная логика сохранена дословно:** порядок проверок при продаже,
формула кассы смены, заморозка закрытой смены, идемпотентность чека,
оптимистическая блокировка остатка, атомарные `UPDATE` вместо
«прочитал — изменил — записал», защиты от удаления с историей, намеренное
сокрытие маржи от менеджера и кассира.

## Чего нет

- **Telegram-бот.** Требует постоянно живущего процесса. На shared-хостинге
  он не работал и в Python-версии.
- **Обновление из приложения.** Эндпоинты оставлены (фронтенд их вызывает),
  но честно отвечают, что функция выключена.

## Что исправлено по дороге

- **Отказ менеджера при скидке списывал товар.** В Python проверка пароля
  шла внутри цикла по корзине и при неудаче делала `commit()`, сохраняя уже
  списанные остатки предыдущих позиций. Теперь всё читается и проверяется
  до первой записи.
- **F5 на «Созламалар» показывал сырой JSON.** Пути `/settings`, `/sales`,
  `/suppliers` — одновременно страницы React и эндпоинты API. Теперь они
  разделяются по заголовку `Accept`.
- **Графики делали по запросу на каждый день** (график за 30 дней — 90
  запросов). Теперь один запрос с `CASE` независимо от числа дней.
- **Список чеков делал запрос на каждый чек** (N+1). Теперь четыре запроса
  на любую длину списка.
- **Показатели сотрудников** — два запроса вместо двух на каждого сотрудника.
- **Фильтр по датам в «Давомат»** резал сутки по UTC, а не по времени
  магазина.

## Структура

```
app/
  bootstrap.php   загрузка .env, проверка SECRET_KEY, обработчики ошибок
  Http.php        ответы и проверка входных данных
  Db.php          PDO, атомарные UPDATE, переносимость между MySQL/PgSQL/SQLite
  Auth.php        JWT, пароли passlib, сессии, ограничение попыток
  Tz.php          единственное место, где время переводится между UTC и магазином
  Router.php      маршруты; грузится только нужный файл
  Shape.php       формы ответов — контракт с фронтендом
  Schema.php      таблицы, индексы, миграции
  Audit.php       журнал действий
  Cache.php       короткий кэш тяжёлых выборок (APCu или файлы)
  Xlsx.php        Excel и CSV без внешних библиотек
  Backup.php      резервные копии на чистом PHP
  routes/         11 файлов по числу разделов API
bin/
  setup.php       создать/обновить схему и первого админа
  migrate.php     перенос данных из старой базы
  backup.php      резервная копия для cron
public/
  index.php       единственная точка входа
  .htaccess       статика мимо PHP, кэш, сжатие
  .user.ini       opcache, realpath-кэш, сжатие, лимиты
  uploads/        фото накладных (код здесь запрещён отдельным .htaccess)
```

Роутер грузит только тот файл, который соответствует первому сегменту пути:
запрос к `/sales/` читает `routes/sales.php`, остальные десять файлов с диска
не берутся.

## Разработка

```bash
cp .env.example .env          # DATABASE_URL=sqlite:./market.db для локальной работы
php bin/setup.php
php -S 127.0.0.1:8000 -t public public/index.php
```

Пересборка интерфейса:

```bash
cd ../frontend && npm run build && cp -r dist/* ../php/public/
```

Проверка синтаксиса перед выкладкой:

```bash
find app bin public -name "*.php" -exec php -l {} \;
```
